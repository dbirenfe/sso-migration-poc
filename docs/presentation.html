Zero-code-change approach to running two identity providers side by side during a gradual Keycloak migration.

The Problem

Customer migrating from RH-SSO 7.6 to RHBK 26.4 — but can't do it all at once.

The Scenario
  • System A has a client on RH-SSO. Users authenticate through it.
  • System B has no client — uses System A's client to get tokens and pull data.
  • After migrating System A to RHBK, System B's RH-SSO tokens become invalid.
Critical Constraint

The customer can't tell us which app uses which client or which IdP.

Requirements: gradual migration, zero code changes, no per-app mapping.

Foundation: Bidirectional Token Exchange

RFC 8693 — one IdP validates a foreign token and issues a native token in return.

RH-SSO 7.6 Configuration
  • IdP alias: rhbk
  • Client: token-exchange-client
  • Features: token_exchange + admin_fine_grained_authz

Both are tech-preview, enabled via JAVA_OPTS_APPEND

RHBK 26.4 Configuration
  • IdP alias: rhsso
  • Client: token-exchange-client
  • Features: preview + admin-fine-grained-authz:v1

Must disable token-exchange-external-internal (v2 conflicts)

Key Gotcha

The :v1 suffix on admin-fine-grained-authz is critical — without it, the feature silently fails.

Evolution 1: Proxy in Front of Apps

Built a transparent Python reverse proxy between callers and backend services.

How It Worked
  • Configure EXPECTED_ISSUER — the issuer the backend expects
  • Decode the Bearer token's iss claim
  • If issuer doesn't match → exchange the token
  • Forward with the new token
token-proxy-legacy

In front of RH-SSO apps. Exchanges RHBK → RH-SSO tokens.

token-proxy-migrated

In front of RHBK apps. Exchanges RH-SSO → RHBK tokens.

Worked in our POC. But at the customer site...

The Customer's Curveball

Blocker: They couldn't map which app uses which client or IdP.
  • Dozens of apps across multiple namespaces
  • App teams couldn't tell us which SSO client their app used
  • EXPECTED_ISSUER required knowing which IdP each app validates against

We needed an approach that requires zero per-app knowledge.

Evolution 2: IdP Gateway Mode

Breakthrough: proxy the IdPs themselves, not the apps.

One proxy in front of RH-SSO, one in front of RHBK. All traffic flows through.

Try-First, Exchange-on-Failure
  1. Forward the request to the IdP as-is
  2. If IdP returns 401/403 AND request has Bearer token → exchange
  3. Retry with the exchanged token
  4. If retry also fails → token is genuinely invalid

No per-app config — proxy knows nothing about apps

No issuer check — the IdP tells us via 401

How Requests Flow

Pass-through Valid Token
App → Proxy → IdP → 200 OK → Proxy → App

No exchange needed. Sub-millisecond overhead.

Exchange Wrong-IdP Token
App → Proxy → IdP → 401 ↓ Proxy catches 401 + Bearer ↓ Exchange token at IdP ↓ Retry with new token IdP → 200 OK → Proxy → App

App never knows. 20-100ms overhead (cached after first exchange).

Key Deployment Details

  • Proxy routes take over IdP hostnames (edge TLS termination)
  • RHBK operator ingress disabled: spec.ingress.enabled: false
  • TLS trust via ConfigMap-mounted certificates (survives restarts)
  • IDP_EXTERNAL_HOST ensures correct issuer (no :8443)

Bugs That Almost Broke Everything

Bug 1: :8443 Issuer

Internal calls produced tokens with :8443 in the issuer. Fixed with IDP_EXTERNAL_HOST — sets Host header on exchange calls.

Bug 2: Login Loop

Python requests merges duplicate Set-Cookie headers. Fixed by using raw.headers from urllib3.

Bug 3: TLS Trust

IdPs couldn't validate each other's certs. Fixed with ConfigMap-mounted certs + X509_CA_BUNDLE / truststore-paths.

Lesson Learned

Python's requests library is not designed for proxying — it's an HTTP client. For faithful proxying, use urllib3's raw headers.

Key Takeaways

  1. "Try first, exchange on failure" — more robust than issuer pre-checking, zero per-app config
  2. token-exchange-external-internal v2 conflicts with v1 — disable v2
  3. Python requests is not a proxy — use raw.headers for Set-Cookie
  4. Internal URLs = wrong issuer port — set IDP_EXTERNAL_HOST
  5. RHBK operator recreates routes — disable with ingress.enabled: false
